# truthscale: build plan

## The thesis, in one paragraph

`nvidia-smi` reports "GPU utilization" and NVIDIA defines it as *the percent of
time over the sample period during which one or more kernels was executing*. It
is a time-based occupancy flag, not a measure of work. One tiny kernel on 1 of
an H100's 132 streaming multiprocessors, running the whole window, reads **100%**
while 131 SMs sit idle. Autoregressive LLM decode is the pathological case: it
launches one small kernel per token, so `GPU_UTIL` pins at 100% while SM
occupancy sits near 15% and the tensor cores are close to idle.

Production Kubernetes clusters average around **5% real GPU utilization** while
their dashboards read healthy. KEDA and Karpenter then autoscale on the number
that caused the confusion.

**truthscale measures what each node can actually deliver, reports the gap
between that ceiling and what it is delivering, and makes that gap the signal
you scale on.**

## Why this project and not the others

| Considered | Why not |
|---|---|
| Agentic token observability | Langfuse, Helicone, LangSmith, OpenLLMetry, Phoenix, and ccusage already occupy it. Differentiation would have to be earned against six incumbents |
| Generic GPU dashboard | NVIDIA's GPU Operator, DCGM Exporter, and GPU Usage Monitor already do this, and all three export the misleading number |
| A new scheduler | Kueue and Volcano are good and this is not the gap |

The gap is narrow and real: **the honest signal does not exist as an installable
thing.** It is discussed in blog posts and absent from every shipped tool.

## Relationship to gpu-truth

`eprecisio/gpu-truth` (private) is the measurement research: it establishes a
hardware ceiling, measures what the serving stack delivers on top, and reports
the gap. It is a one-shot `make` harness for one hardware pilot, and it stops at
a PDF.

`truthscale` is the productization: the same measurement, running continuously
in a cluster, exposed as metrics, and turned into a decision.

**Hard boundary.** gpu-truth contains client pilot results. Nothing from
`results/`, `reports/generated/`, or any client hardware fingerprint enters this
repository. What crosses is *methodology*: which counters to read, how to
establish a ceiling, and the three honesty rules. Those are ideas, not data.

## The design decision that determines whether anyone uses this

**A GPU tool nobody can run is a GPU tool nobody stars.** Most people
evaluating this will not have a spare H100, and will not attach one to try a
stranger's binary.

So `--replay` is a first-class feature, not a test fixture. Recorded traces
ship in the repository, and every command works against them:

```bash
truthscale top --replay traces/h100-vllm-decode.jsonl
```

That runs on a laptop, in CI, and in a `kind` cluster. It is how the README
demo works, how the tests work, and how a reviewer forms an opinion in 30
seconds. Traces are synthetic or anonymized, generated by a committed script,
never lifted from a client run.

## Architecture

```
  ┌─────────────────────────────────────────────────────────┐
  │ DaemonSet: truthscale-agent (one per GPU node)          │
  │                                                          │
  │  collector ── DCGM fields ──┐                            │
  │  collector ── vLLM /metrics ┼── correlate on one clock   │
  │  collector ── node/thermal ─┘         │                  │
  │                                        ▼                 │
  │                              ceiling store (per node)    │
  │                                        │                 │
  │                                        ▼                 │
  │                              honest signal computation   │
  └──────────────────────┬───────────────────────────────────┘
                         │
        ┌────────────────┼────────────────┐
        ▼                ▼                ▼
   /metrics          truthscale top    decision engine
   (Prometheus)      (live TUI)        (v0.3)
```

Three collectors, one monotonic clock. That last part is a rule taken from
gpu-truth: a throughput dip is only attributable to software if the GPU samples
from the *same instant* rule out power and thermal throttling.

## The honest metric set

The point is the pairing. Each row shows the number people use next to the
number that means something.

| What people watch | What truthscale reports | Source |
|---|---|---|
| `DCGM_FI_DEV_GPU_UTIL` | `sm_occupancy` | `DCGM_FI_PROF_SM_OCCUPANCY` |
| GPU memory used | `dram_active` (bandwidth actually moved) | `DCGM_FI_PROF_DRAM_ACTIVE` |
| "it is busy" | `tensor_active` | `DCGM_FI_PROF_PIPE_TENSOR_ACTIVE` |
| requests/sec | `tokens_per_second` and `batch_efficiency` | vLLM `/metrics` |
| nothing | `kv_cache_utilization` | vLLM `/metrics` |
| nothing | `queue_depth` and time-in-queue | vLLM `/metrics` |
| nothing | `throttle_reason` (power, thermal, sync boost) | `DCGM_FI_DEV_CLOCK_THROTTLE_REASONS` |
| nothing | **`ceiling_ratio`: delivered ÷ measured ceiling** | derived |

`ceiling_ratio` is the headline number and the only one that answers "should
this node exist?".

## Non-negotiable rules, inherited from gpu-truth

Enforced in code and in review, not encouraged in a doc:

1. **No missing measurement is replaced by an estimate.** A field DCGM did not
   return is absent, never zero. Zero and unknown are different, and conflating
   them is how a dashboard lies.
2. **No throughput decline is attributed to software before power and thermal
   throttling are ruled out** from the samples at that instant.
3. **Raw records, not averages.** Samples are written as they were taken.
   Percentiles are computed on read, never at capture time.
4. **Spec-sheet figures and measured figures never share a column.** The ceiling
   is what this node did, not what the datasheet claims.

## Scope

### v0.1: the honest number, and proof it is honest

Deliberately not an operator yet. A repo that overreaches on its first release
is one nobody can evaluate.

- [ ] `truthscale` single static binary, Go, no CGO, no runtime dependencies
- [ ] `truthscale measure`: establish this node's ceiling with a short, bounded,
      cancellable microbenchmark. Refuses to run if another process holds the GPU
- [ ] `truthscale top`: live per-GPU view, ceiling-relative, the lie and the
      truth side by side
- [ ] `truthscale explain`: why the two numbers differ on *this* sample, in
      words. The teaching command, and the one people will screenshot
- [ ] `truthscale export`: Prometheus endpoint
- [ ] `--replay` on every command, with committed traces and a generator script
- [ ] Helm chart: DaemonSet, ServiceMonitor, optional Grafana dashboard
- [ ] Works on a laptop with no GPU, and on `kind`, via replay
- [ ] Docs: the thesis, every metric with its DCGM field and units, the hazard
      register
- [ ] CI: build, test, lint, `helm template` and `helm lint`, replay smoke test

### v0.2: continuous, and alerting

- [ ] Run as a DaemonSet against real DCGM in-cluster
- [ ] Ceiling re-measurement on a schedule and on node-label change
- [ ] Prometheus alerting rules that are worth paging on, with rationale
- [ ] Slack and generic webhook sink
- [ ] Grafana dashboard as a real artifact, not a screenshot

### v0.3: the decision engine

The intellectual centre, and last on purpose: it needs the signal to be trusted
first.

- [ ] A documented, testable decision function: given ceiling ratio, queue
      depth, KV cache pressure, and throttle state, recommend scale up, scale
      down, rightsize, or do nothing
- [ ] `truthscale recommend`, dry-run, explaining each recommendation
- [ ] CRD plus controller, so a recommendation can become an action
- [ ] RKE2 and Cluster Autoscaler integration
- [ ] **Recommendations require opt-in before they actuate anything.** A tool
      that resizes a GPU fleet on its own the day it is installed is a tool
      nobody installs

### Explicitly not planned

- A scheduler. Kueue and Volcano exist and are good
- A replacement for DCGM. This reads DCGM; it does not reimplement it
- Vendor lock-in to one cloud. The signal is node-local
- A hosted service
- Actuation without opt-in

## Risks, and what is done about each

| Risk | Mitigation |
|---|---|
| Nobody can try it (no GPU) | `--replay` with committed traces, first-class |
| The ceiling benchmark disrupts a production workload | Refuses to run when the GPU is held; bounded duration; explicit opt-in flag |
| DCGM profiling fields are unavailable on some GPUs or drivers | Detect and report absent, never substitute. Documented support matrix |
| It reads as a dashboard, not a decision tool | `ceiling_ratio` is the headline, and `explain` is a first-class command |
| Leaking client data from gpu-truth | Methodology crosses, data does not. Secret scan in CI and a stated boundary |
| Scope collapse into a half-built operator | v0.1 ships no operator at all, on purpose |

## Success criteria

Not stars. Whether these are true:

1. Someone with no GPU can understand the thesis and see the demo in 60 seconds
2. Someone with a GPU can install it and get a `ceiling_ratio` in 10 minutes
3. `truthscale explain` teaches a reader something they did not know
4. Every number is traceable to a DCGM field or a derived formula in the docs
5. It is honest about what it cannot measure
