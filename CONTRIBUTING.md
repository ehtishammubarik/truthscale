# Contributing to truthscale

This tool exists because a widely-trusted number is misleading. If it ever
becomes misleading itself, it is worse than nothing, because it will be believed
for the same reasons.

## Before you start

**Open an issue first** for anything beyond a typo. A paragraph agreeing the
approach is cheaper than a review of the wrong implementation.

**Say on the issue that you are taking it, before you write code.** One comment.
It costs ten seconds and it is the only thing between you and building something
someone finished yesterday. If you drop it, say so; nobody minds and it frees
the issue.

**One issue per pull request.** Exactly one `Closes #N`, or `Refs #N` for
deliberate partial work. A PR closing several issues cannot be reviewed,
reverted, or released per issue, and a reviewer has to hold several unrelated
arguments at once, which is how a bad change gets waved through beside two good
ones.

Finding a second defect mid-branch is normal. File it, finish what you claimed,
open the next PR. **Do not widen the branch in flight**, even when the two share
a root cause. Shared cause is an argument for a shared explanation, not a shared
commit.

## The four rules

Enforced in code and in review. A PR that breaks one of these is declined on
principle, not on taste.

**1. A measurement that was not taken is never rendered as zero.**

Use `collect.Metric`. Never a bare `float64` for anything that might be
unavailable, and never `0` as a sentinel. Absence has to survive a JSON round
trip, and there is a test that asserts it. If you find yourself writing
`m.Or(0)` in arithmetic that feeds a verdict, stop: `Or` is for rendering.

An idle GPU and an unsupported driver must not look identical. They do on most
dashboards, and that is the bug this project is named after.

**2. Hardware is ruled out before software is blamed.**

A sample with any throttle flag short-circuits every other verdict. Do not add a
code path that reaches a conclusion about software efficiency from a sample where
the GPU was being held back by power or heat.

**3. Raw records, not averages.**

Samples are written as taken. Percentiles are computed on read. A capture path
that averages has destroyed the data an investigation needs, and the loss is not
recoverable.

**4. Measured and declared never share a column.**

A ceiling is what this GPU did on this node under this driver. A datasheet figure
is not a ceiling, and `ceiling.Trustworthy()` exists to enforce that. Do not add
a fallback to a spec-sheet number: a ratio against a denominator nobody measured
is wrong in an unknown direction, which is worse than absent.

## Setup

```bash
git clone https://github.com/ehtishammubarik/truthscale && cd truthscale
go build ./... && go test ./...
```

No GPU needed, and none is used by the test suite.

## Before you open a PR

```bash
go build ./...
go test -race ./...
go vet ./...
gofmt -l .                        # must print nothing
go run ./cmd/gen-traces           # then: git diff --exit-code traces/
```

All five must pass. CI runs them, plus a job that runs the README demo on a
runner with no GPU, because "try it without a GPU" is a load-bearing claim.

If a tool is not installed, say so in the PR rather than implying it passed.

## Tests

**Write the test so you have watched it fail.** Break the fix, see it go red,
put the fix back. A test never observed failing is not yet a test.

**Assert the property, not the string.** A test that pins exact output breaks on
a column-width change, which is noise, and passes against a renderer that prints
a fabricated zero, which is the actual bug.

New behaviour that touches a verdict needs a synthetic scenario in
`internal/synth`, so the behaviour is exercised end to end through the same path
the README demo uses.

## Traces

Traces in `traces/` are **synthetic** and generated by `cmd/gen-traces` from
published behaviour and the counter semantics in `docs/metrics.md`.

**Do not commit a trace captured from a real deployment.** Not anonymized, not
trimmed. A trace carries model names, node names, memory footprints, and request
timings, which together describe somebody's infrastructure and workload. The
generator is deterministic so committed traces are reproducible and a diff to
them is meaningful.

If you have real hardware and want to contribute a shape, contribute the
*generator change* that reproduces it and say what you observed.

## Commit messages

```
type(scope): imperative summary under 72 chars

Why, not what. The diff says what.

Closes #123
```

Types: `feat`, `fix`, `refactor`, `perf`, `docs`, `test`, `build`, `ci`, `chore`.
One logical change per commit. If the summary needs "and", split it.

If you deliberately left part of an issue undone, say so in the commit and file
the remainder. A boundary stated is a boundary; a boundary implied is a surprise
for the next reader.

## A note on CI

If this is your first contribution, GitHub holds your workflow runs until a
maintainer approves them. Until then the checks read **"no checks reported"**,
which looks like a pass and is not one. Ping the PR if it sits unapproved, and do
not treat a local run as a substitute for the matrix.

## Security

Never commit credentials. Report vulnerabilities to
[contact@eprecisio.com](mailto:contact@eprecisio.com) rather than in a public
issue.

## If this is useful to you

Star the repo. It is the main way anyone else finds this, and a project that
looks unused gets treated as unmaintained regardless of the state of its tests.

Entirely optional, and unrelated to whether your PR is merged. Code is reviewed
on the code.
